# DynamisGPU 1.1.0

Version 1.1.0 adds a measured `FUSED_FMA` device capability, fixes four defects found by the vectrix GPU data-contract
survey, and adds CI that runs the Vulkan backend on a real driver. It is distributed through GitHub and local Maven
installation. It is not published to Maven Central.

## New

- **`GpuCapabilities.FUSED_FMA`:** whether `fma` computes `a*b + c` with one rounding.
  - **Why:** Vulkan does not require it, and Mesa's lavapipe rounds twice. A kernel that ports a CPU `Math.fma` can
    only match it bit for bit where `fma` is fused.
  - **Where it's reported:** `GpuDevice.capabilities()` reports it after a one-dispatch probe, run on the first call
    on the device's owner thread. Adapters do not report it, because measuring it needs a device.
  - **Where it holds:** native Metal and MoltenVK report it on Apple GPUs; lavapipe and the mock don't.
  - **Using it:** list it in `PipelineDescriptor.requiredFeatures` to have pipeline creation fail with `UNSUPPORTED`
    where it's absent. Only such pipelines run the probe.
- **`GpuCapabilities.withShaderFeatures(Set)`:** returns a copy of the capabilities with extra features.
- **`IndexType` on ray-tracing build inputs:** a new `GpuRayTracingBuildInputPayload.of` overload takes an
  `IndexType`.
  - **Defaults:** the existing overloads default to `UINT32`.
  - **BLAS builds:** they use the payload's index type for the Vulkan index type and for `firstIndex` byte offsets.
  - **Checks:** the index offset must be a multiple of the index size, and `UINT16` payloads reject
    `maxVertexIndex > 0xFFFF`.
- **CI** (`.github/workflows/ci.yml`): the portable build, plus the Vulkan compute conformance suite on Mesa's lavapipe,
  for every push.

## Fixed

- **Meshlet bounds were byte-swapped.** `GpuMeshletBoundsPayload` read every input big-endian, so little-endian floats
  reached the GPU with their bytes reversed: `1.0` arrived as `4.6006E-41`. It now keeps the source byte order.
- **The culling frustum contract was contradictory.** `ComputeCullingDispatch` documented 6 × vec4, while the Vulkan
  dispatch required 6 floats. It is now `FRUSTUM_PLANE_FLOATS = 24`: six planes of `(a, b, c, d)`, the layout of
  Vectrix `FrustumPlanes.getVec4Array`.
- **Ray-tracing index types were hard-coded,** as described under New.
- **TLAS instance fields were truncated silently.** `GpuRayTracingTlasInstanceMetadata` now rejects values wider than
  Vulkan's fields: the custom index and shader-binding-table offset are 24 bits, the flags 8 bits.
- **`VertexLayout` overflowed.** An offset near `Integer.MAX_VALUE` wrapped past the stride check.

## Behaviour changes to check

- **Culling:** `VulkanComputeCullingDispatch` and `MockComputeCullingDispatch` now require exactly 24 floats. A caller
  passing 6 now gets `IllegalArgumentException`. LightEngine's `VulkanCullingComputePass`, the only implementation
  outside this repository, is unaffected.
- **TLAS metadata and `VertexLayout`:** values that used to be silently truncated or accepted are now rejected.
- **Test helper:**
  - **Kernel layout:** the `fp_strict` conformance kernel writes four outputs per element.
  - **New hooks:** `ComputeConformance` has `strictWithoutPreciseMarks()` and `expectedFusedFma()`. Only its
    subclasses see them.
  - **Precise marks:** the floating-point test checks operations marked `precise` on every backend, and unmarked ones
    only where the backend promises strict defaults (Metal, and MoltenVK with fast math off). GLSL lets a Vulkan
    driver reassociate unmarked arithmetic, and lavapipe does.
- **Device capabilities:** `ComputeDevice.capabilities()` can now include measured features. Validation limits still
  come from the adapter.

## Numerical scope

[compute-runtime.md](../compute-runtime.md) covers the numerical scope:
- **Fused `fma`:** it is not guaranteed on Vulkan; check `FUSED_FMA`.
- **Marking `fma`:** mark `fma` calls `NoContraction` where their rounding matters. Mesa otherwise rewrites
  `fma(k, a, fma(k, b, c))` into `fma(k, a + b, c)`.
- **Strict defaults:** Metal and MoltenVK round even unmarked arithmetic as written. Other Vulkan drivers do that only
  for operations marked `NoContraction`.

## Install and consume

All public artifacts use version `1.1.0` under `org.dynamisengine`:

- `dynamis-gpu-api`
- `dynamis-gpu-metal`
- `dynamis-gpu-vulkan`
- `dynamis-gpu-test` (optional testing helper)
- `dynamisgpu-parent` (parent POM)

The external `dynamis-parent` stays at `1.0.1`.

```sh
gh release download v1.1.0 --repo ljramones/DynamicGPU \
  --pattern 'dynamisgpu-1.1.0-maven.zip' --pattern SHA256SUMS
shasum -a 256 dynamisgpu-1.1.0-maven.zip
unzip dynamisgpu-1.1.0-maven.zip
sh dynamisgpu-1.1.0/install.sh
```

Compare the ZIP digest against `SHA256SUMS` before installation. Existing 1.0.x artifacts are unchanged. The
class-path JVM flag remains `--enable-native-access=ALL-UNNAMED`.

- **Portable build:** passes (220 tests; the hardware-only tests are skipped).
- **Conformance suite:** passes on every target:

  | Target | Driver | Tests |
  |---|---|---|

  | MoltenVK | 1.4.1 on the same machine | 15 |
  | Mesa lavapipe | Linux x86_64 in CI; Linux arm64 in a local container | 15 |

- **vectrix-gpu:** its suite passes against this version on Metal and MoltenVK.

Reproduce packaging without Central publication using `scripts/package-release.sh` with the Vulkan SDK configuration
from the [runtime guide](../compute-runtime.md). The included bridge targets macOS 13.0 arm64. The stricter runtime MSL
behaviour requires macOS 15+. Offline metallib generation and loading remain unverified.
