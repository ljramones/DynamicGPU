# DynamisGPU 1.5.0 (unreleased)

Draft notes, collected as the work lands. Milestone 1.5 of the [roadmap](../roadmap.md): runtime I, memory and
replay.

## New

- **Memory pools:** buffers are sub-allocated from pooled blocks, per placement.
  - **Blocks:** 64 MiB each; buffers over 16 MiB get their own block.
  - **Staging:** transfer staging comes from the pools too.
  - **Allocator:** `MemoryPool` (spi) is a backend-neutral allocator: first fit, freed ranges merged, one empty block
    kept.
  - **Measured on an M4 Max:**
    - 1,000 small buffers make one driver allocation.
    - Allocating and closing a buffer is 5.3 times faster on native Metal (1,781 to 336 ns) and 12.7 times faster
      on MoltenVK (9,908 to 782 ns).
- **`GpuDevice.memoryStats()`** (`MemoryStats`): blocks held, bytes used, live allocations, and driver allocations
  so far.
  - **Budget:** it also gives the device's memory budget and usage, with `headroomBytes()`. Vulkan uses
    `VK_EXT_memory_budget`, now enabled where present; Metal uses `dg_device_memory`.

- **Recordings:** `GpuCommandEncoder.record()` and `GpuQueue.submit(GpuRecording)` record a command list once and
  run it many times.
  - **Changing it:** `GpuRecording.parameters`, `bind` and `groups` change dispatches between runs.
  - **Vulkan:** it keeps the command buffer and descriptor sets across runs. Submission on lavapipe fell from about
    200 µs to 30–35 µs for 50 dispatches.
  - **Lifetime and rules:** see [compute-runtime.md](../compute-runtime.md).
- **Per-dispatch timing:** `GpuCommandEncoder.profile()` and `GpuSubmission.dispatchTimes()`.
  - **Vulkan:** timestamp pairs.
  - **Metal:** per-dispatch encoders with counter samples (`dg_batch_profile`, `dg_dispatch_times`). Its times include
    queued time; see the runtime guide.
- **Vulkan pipeline cache:** always used in memory, and persisted with `-Ddynamisgpu.pipelineCache=<directory>`. On
  MoltenVK, three pipelines in a later run took 13.3 ms instead of 21.6, and a repeat in-process took 1 ms instead of
  4.3.
- **Blocking waits:** `GpuSubmission.await` blocks on the driver's completion signal (`vkWaitForFences`; Metal
  completion handler, bridge ABI 4 `dg_wait`) instead of polling. On an M4 Max a 4 KiB round trip fell from 155 to
  103 µs on Metal, and from 249 to 202 µs on MoltenVK.
- **Metal:** consecutive dispatches share one compute encoder.
- **Vulkan:** barriers cover compute and transfer stages instead of all commands.

## Behaviour changes to check

- **New interface methods with defaults:** `GpuQueue` and `GpuCommandEncoder` gain default methods (`submit(GpuRecording)`,
  `record()`). `ComputeDriver` gains `prepare` and `submit(Prepared, ...)`, which re-submit the command list by
  default.
- **Metal bridge ABI 4:** it adds `dg_wait`. A bridge built from earlier sources is refused with an ABI mismatch.

- **A new buffer's contents are undefined.** Pooled memory is reused, so fill or upload before reading. Vulkan
  never promised zeroed memory either.
- **Vulkan:** host-visible blocks stay mapped for their lifetime, and every pooled buffer is created with every
  buffer usage.
- **Metal uploads and fills:** they copy through pooled shared staging instead of the bridge's per-call buffers
  (`dg_upload` and `dg_fill` are no longer called).
